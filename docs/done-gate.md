# The done gate and the other checks: the detail

The full text of the checks' rows of STATE.md → What works today (its Quality rows whose Where / why cell is over 600
characters): how each check works, where it runs, and what still gets past it. STATE.md keeps each row's status and a
short cell that points here; each section below is that row's whole cell, moved here word for word on 2026-10-15

## Automated tests and CI

.github/workflows/ci.yml: a pull request runs only the quick checks; the merge queue's build and every push to main also run the whole suite and the four-runs-at-once test, so a pull request that breaks them is caught in the queue, not before it; green CI does not mean a customer-facing feature works. A test run makes and deletes only its own companies and queued jobs (tests/test-companies.ts; the done rules refuse a test that deletes companies or queued jobs any other way), a test that starts the worker's job runner gives it a pg-boss schema of its own (services/worker/test/fixtures/test-job-schema.ts), the dev-login tests take turns across runs (tests/dev-login-lock.ts), and no test drops a database trigger (the done rules refuse one), because on the local stack every trigger drop locks all of the sign-in server's tables and deadlocks other runs' sign-ups; the apply-poison test's fault trigger is installed once per database and left there (one trigger on `tasks` that fails only a task titled with the test's sentinel): four whole-suite runs started at once all pass and leave another company's data and queued calls and the dev login's workspaces as they were (services/worker/test/test-runs-at-once.test.ts, run alone by CI's at-once job in the merge queue's build before every pull request lands and on every push to main (it is held back from pull requests), and by Slice 0's proof; since [#166](https://github.com/Peertopeer-solutions/revenue-os/pull/166) CI runs three jobs at once, each on its own fresh local stack of only the database, sign-in, data interface and gateway (.github/test-stack.sh): the quick checks, the whole suite as the Mac runs it, and that test alone, and `checks` passes only when all three did, or, on a pull request only, when the quick checks did and the other two were held back (scripts/done-gate/ci-jobs.ts); the Mac's `bun run gate` leaves it out of its whole-suite run by its path, `bun run gate tests --leave-at-once-to-ci`, and its summary says "not run here, left to CI", since [#163](https://github.com/devesh911/revenue-os/pull/163), so a local gate starts one whole-suite run instead of five and a demo; a worker running on this machine works every company's due jobs, so that test refuses to start while one runs, naming each and the `kill` that stops it: scripts/done-gate/running-workers.ts; and when its runs take longer than its time limit allows, it fails a minute early, naming what ran late and the machine's load average, before it compares anything: at bun's own limit the file's clean-up ran under the comparison, which then reported the other company's audit, usage and queued jobs as deleted: tests/deadline.ts); a test's child processes started through tests/children.ts, that test's whole-suite runs among them, run in process groups of their own: a child's group, with everything the child started, is stopped when the child ends, and every group when the test file ends, however it ends (its time limit, SIGTERM, Ctrl-C, process.exit), so none outlives the test; only a SIGKILL of the test run itself still leaves them running; a browser test that passes only on a retry fails CI. Still shared: while scripts/dev-login.test.ts runs (a few seconds) the one dev login is also admin of its short-lived test workspaces, which carry the seed workspaces' names, so a console sign-in or a browser-check run that starts then can open one that is deleted moments later; and the browser checks' setup (apps/console/e2e/global-setup.ts) reseeds the dev login's real-estate workspace on every run, and that seed deletes any hand-made contact there that copies a seed person's name and source (supabase/seeds/real_estate.sql)

## The checkpoint a restarted session is shown

`bun run gate checkpoint --done … --failed … --next …` (scripts/done-gate/checkpoint.ts) keeps it per checkout and branch in the gate's record, and the gate adds the request itself: Devesh's typed messages from Claude Code's transcripts of the sessions that wrote it (oldest first; when too long to show whole, his first and his newest), else the branch's roadmap item; the done gate's session-start hook (.claude/settings.json; scripts/done-gate/session-start.ts) shows it to every session that starts in that checkout, and reminds a branch that records an item but has no checkpoint; a session that started elsewhere is shown it before its first command or edit in that checkout, which is refused once for it (scripts/done-gate/hook.ts); a stop on a branch that builds an item is sent back until the checkpoint was written on the code the session leaves, so it is kept up to date (AGENTS.md → The loop, step 2; [#133](https://github.com/devesh911/revenue-os/pull/133)). Missing: Codex runs the same hooks (.codex/hooks.json), but whether it shows a session-start hook's added context to the agent is unverified, and a Codex session's request is the roadmap item, since the gate reads only Claude Code's transcripts; the transcript is a file the agent could append to, so a line it adds claiming to be typed by Devesh is shown as his words, as in the verifier's hand-over (next row); the request holds every message of the sessions that wrote it, those about an earlier item included; not yet seen in a live session (the Slice 0 proof)

## The examples agents copy

scripts/guards/pattern-files.ts, run by `bun run guards` in CI and the done gate, fails a pattern file (in any folder under docs/patterns/) holding a code block that is not an excerpt of a file git lists (fenced with ``` or ~~~, at the top level, in a list item or in a quote; indented; or an HTML `<pre>` block), an excerpt whose lines no longer sit together and in order in its file (a `…` line marks where lines are left out), an excerpt of a link or of a file in a linked folder, a name of a file or folder git doesn't list, and a checkout with no pattern files. Names are looked up in `git ls-files`, never on disk, so the guard never reads a file outside the repository or an ignored one, and judges the same here as in CI. Not checked: whether an example is safe (the "do not copy" marks on the route and background-job patterns, and on the Vapi receiver in the worker-webhook skill, are written by hand), code written inside a line of prose (`withOrg(…)` in backticks) and names inside an excerpt, which are the real file's own

## Every query names its company

scripts/guards/company-filter.ts, run by `bun run guards` in CI and the done gate, reads every `.query(` call in apps, services, packages and scripts (tests, the gate and guards, the proof steps, the local tools that run as the database's owner, and scripts/evals.ts left out: its NOT_PRODUCT list; evals.ts runs on the product login but finds its company by slug, a read across companies that finds none today, so it stays out until that lookup is fixed) and fails one whose SQL isn't a single literal at the call, holds a ${…} piece, or reads, changes or deletes a table without `org_id = $n` as an and-condition of its own where or join (shared template tables may add `or org_id is null`; orgs needs id = $n), an insert without org_id, an upsert whose do update leaves the company out, a table in an unknown schema, profiles or platform_operators. Known holes: it checks SQL text, so it can't tell that $n holds the request's company (the rules-off tests cover only the reads, checks and jobs the tenant-isolation row names); SQL inside database functions is checked only by tests/rls_coverage.sql's schema rules; a query reached by destructuring or by bracket is not seen

## Every added line is run by a test

`bun run gate tests` (in the done gate and in CI's `checks`) runs bun's tests with `--coverage --coverage-reporter=lcov` and fails when a line the change adds since origin/main to a .ts or .tsx file under apps, services or packages (test files and .d.ts files aside; a tool's settings file such as vite.config.ts counts) did not run (scripts/done-gate/coverage.ts), read by the line rule in scripts/done-gate/lcov.ts: a line ran only when Bun marks it run and also the nearest earlier line its report lists, because Bun 1.3.11 marks a function's last line run even when it never ran. A file the report doesn't name counts as not run at all, unless it holds only types; there a line counts unless nothing but brackets is left once its comments are gone (scripts/done-gate/code-lines.ts). Exempt: lines the change only moves, found by git's moved-code detection with the options the done-rules item names (the snapshot marks each moved line, scripts/done-gate/moved.ts), and a run of changed lines that edits only comments, every line's code left as it was (scripts/done-gate/comment-edits.ts). A new migration needs a database test the same change adds or edits whose code, comments not counting, names what it adds, a cross-company denial test for a new table (scripts/done-gate/migration-tests.ts says how that is read, and its limits: it reads names, so a test that names a table without asking another company for it passes). A gap is marked on its line, `// coverage gap: <why>`, or, for console code only the browser checks reach, `// coverage: browser-only (<an existing .e2e.ts file under apps/console/e2e>)`; a mark alone on its line covers the line below it instead, the form JSX needs (`{/* … */}` on the line above, which the formatter keeps); each mark is listed in the stop message and CI's log (the done rules' notes, with the line the PR body owes it) and `rules-from-main` refuses a pull request whose body doesn't quote each one (`Coverage mark: <file> · <what it says>`, the file named exactly). The shapes are reproduced on Bun 1.3.11 in scripts/done-gate-coverage.test.ts, which fails when Bun or the pinned version changes, or when this row stops naming one of them. Known holes, not caught: an unused switch `default:`; a never-taken ternary arm on its own line, the first arm or the last; a never-called function written on one line; a later operand of `&&`, `??` or a logical or on its own line, which Bun marks run even when an earlier operand already decided the answer; and the last line of a never-called function or method whose body Bun folds to a constant (`const a = 1; return a;`), which Bun's report doesn't list, so it reads as holding no code (the lines before it are caught, and so is that line when the body isn't folded). Wrongly reported as not run, so marked `// coverage gap: …`: the line after a never-called inner function; the first line of a tested function or method right after a line no test runs (reproduced with a function declared without `export` after one ending in a never-thrown `throw`, as `applyTransitions` follows `drive` in services/worker/src/scheduler.ts, and with a method after a never-called one Bun folds); and a line only a child process runs (an `import.meta.main` entry point a test starts with spawnSync), because Bun's coverage records only the test's own process. A browser-only mark is checked to name a console browser test that exists, not that the test reaches the line

## Migrations already on main

scripts/done-gate/migrations.ts, run through `bun run gate pr` by `rules-from-main` (main's copy, a required check), and locally by `PR_BODY=… bun run gate pr`; seen in scratch repos run as the Slice 0 proof runs it, not yet on a real pull request (main's copy gains it when this merges). It compares each `.sql` file directly in supabase/migrations/ with where the branch left main, so a link swapped in for the file counts as an edit (the folder's README may change). It also refuses a new migration numbered like another as a person reads it (2 is 002), one whose file sorts before main's newest (the cloud would run it in another order than the tests did), and a file in a folder spelled like supabase/migrations/ in another letter case, which a Mac reads as a migration. Numbers are compared within the branch's own code, which holds main's migrations as of the branch's last catch-up; main's ruleset makes a branch catch up before it merges, which runs the check again

## The done gate

scripts/done-gate.ts (its code in scripts/done-gate/, one job per file), run by the Claude Code hooks in .claude/settings.json and the Codex hooks in .codex/hooks.json; CI runs the done rules on every pull request (`bun run gate rules`); humans run `bun run gate`. Product code, which needs the verifier, is every changed file but docs/, Markdown, tests and the gate, CI and hook files (.github/, .codex/, .claude/, scripts/done-gate*), so a change to scripts/ (the guards, seed, demo), package.json, bun.lock, a Dockerfile, Supabase settings or apps/www/index.html needs it too ([#135](https://github.com/devesh911/revenue-os/pull/135)). Since then the done rules also read removed lines: a test file, test or `expect` line a change removes needs a line in docs/removed-tests.md, unless the test moved whole (its first line and its expect lines landing together, as git's moved-code detection sees them) into a file a test runner runs, or was renamed where it stood with none of its expect lines removed, or the expect was rewritten where it stood into one that checks more than a constant, or re-indented in its own test (its body wrapped in a block); an expect is named by its line where the branch left main, as CI's `checks` (which since [#135](https://github.com/devesh911/revenue-os/pull/135) judges the pull request's own commit, not GitHub's merge commit), `rules-from-main` and a stop all number it; each such line, each `done-gate: allow` exception (which needs a reason) and each moved file with its count of moved lines is shown at the stop and in CI's log, and main's copy refuses a PR body that doesn't show each exception and copy each of those lines (scripts/done-gate/removed-tests.ts, moved.ts, pr-quotes.ts); a re-export, and a name added inside a multi-line export list, is checked as an export. A stop judges each checkout the session worked in and was the last to work in (noted before each shell command or edit: its folder, the file, or a checkout the command enters or names by path); a checkout it only looked at, or moved only to commits origin/main holds (a pull, a switch to main), is not judged, but one whose latest commit origin/main does not hold is judged whenever its code changed since the session last accepted it, however it got there (a commit, a switch back after a visit to main, a reset, fast-forward or switch to another branch's commit, and a worktree of the session's branch removed and added again, or moved, judged from what the session last accepted on that branch), so a session reads a pull request in a worktree of its own (scripts/done-gate/only-main.ts, [#132](https://github.com/devesh911/revenue-os/pull/132)). While background work runs (a dev server, a test run, a scheduled job), a stop still runs the done rules, typecheck, lint and guards and asks for the verifier (when a verifier the session started has not stopped yet, as the gate's hooks at its start and stop record it, the agent may stop, marked `NOT verified yet`, and a later stop reads its ruling); only the tests, database policies and browser checks wait, the stop says so (`Done gate ⏳ NOT fully checked yet: …`) and the change is not taken as checked until a stop after the work ends runs them; on a machine without Docker (looked up on the PATH the gate sets; a `docker` that can't print its version counts as none) a stop runs no database checks and is shown as `Done gate ⚠ NOT fully checked: tests, database policies and browser checks did not run here; CI runs them`, never with a ✓, and so is `bun run gate` there (scripts/done-gate/not-run.ts, [#132](https://github.com/devesh911/revenue-os/pull/132)). An agent's `gh pr merge <number>` is refused unless it names the PR's full head commit (`--match-head-commit`), that commit passed the gate on this machine (a stop's pass while background work ran never counts), for product code or a change to .github/workflows/ or the gate's scripts/done-gate/checks.ts, tests-ran.ts, coverage.ts, tests-proven.ts, break-check.ts or merge-gate.ts the verifier ruled PASS on it, while main's ruleset has no merge queue the commit holds main's tip as `git ls-remote origin refs/heads/main` reads it at that moment (an empty, unreadable or failed answer refuses; whether main's rules hold a merge queue is asked of GitHub then too, `gh api repos/<repo>/rules/branches/main`, and an answer that can't be had or read refuses; with a queue the same command queues the pull request and its head need not hold main's tip, as GitHub runs `checks` and `rules-from-main` on it on top of main and the pull requests ahead of it and lands it only when they pass: ci.yml and rules-from-main.yml run on the queue's builds, `merge_group`, the latter reading the queued pull request's head and body from GitHub with its read-only token, scripts/done-gate/github-checks.ts), and GitHub reports `checks` passed on it, asked with a read and counted only from GitHub Actions: until [#163](https://github.com/devesh911/revenue-os/pull/163) only a pass without the database tests, on a machine without Docker, waited for `checks`, but the Mac's gate now leaves the four-runs-at-once test to CI, so every merge waits, on a head CI tested with main as it is; the merge is judged in every folder the command visits before it (each `cd` and `pushd`); `--admin`, a merge handed to a shell or eval, and a pull request, repository or commit written as a variable are refused, and in a line that names gh and merge so is any program but gh, git's own commands, the gate's own command and programs that only read or print text (scripts/done-gate/merge-reading.ts); an MCP tool that merges a pull request, such as the desktop app's auto-merge tool, is refused (.claude/settings.json asks the hook before any MCP tool whose name says merge; not seen in a live session, since that would turn on a real auto-merge); a command or edit that touches the gate's record (.git/done-gate), or runs its hook by hand, is refused and Devesh is told (scripts/done-gate/record-guard.ts, which reads the paths each command is handed, so a message, a search or a question for Devesh may name the record; it stops a careless try, not forgery: code that builds the path from pieces, a script written first and run later, or a folder known only when the command runs still gets past it); a `gh api` command that names the merge address or merge mutation is refused, and so is every other `gh api` write, one that reads its query from a file (`gh api graphql -F query=@file`) included (the next row). Checks on the local database run one at a time across worktrees, but only when run through `bun run gate` or `bun run see`, and the gate starts its own only when no worker runs on this machine (scripts/done-gate/running-workers.ts: it refuses at once, naming each worker's process id and command and the `kill` that stops it, and refuses as well when ps fails or, asked three times, lists nothing, the empty answer of Bun's spawn bug below); two gate runs started at once in two worktrees both pass, their database checks one after the other (scripts/done-gate-at-once.test.ts, with stand-in checks, [#133](https://github.com/devesh911/revenue-os/pull/133)). Under load Bun's synchronous spawn can hand back a git that succeeded with no output (oven-sh/bun#34069): a run whose question for the shared folder gets that empty answer asks again, and stops if it never gets a folder, instead of locking a folder of its own inside its checkout and running beside the holder, and a merge the gate can't find its record for is refused, not let through unchecked ([#143](https://github.com/devesh911/revenue-os/pull/143)); every git question whose answer the gate reads goes through scripts/done-gate/git.ts, which asks once more when an answer comes back empty, so a lost answer no longer reads as no change, no file or no product code: `gate rules` passing a change it never saw, or a product change merging with no verifier ruling ([#146](https://github.com/devesh911/revenue-os/pull/146)). Two lost answers in a row would still read as empty; in the load runs every lost answer came back whole when asked again. The verifier is .claude/agents/verifier.md, Claude only. For each behaviour asked for and each standard edge case that can happen to it (another company, a duplicate, empty input, a failure, a retry), it finds the test at the layer people use (an API or browser test, or a job's or webhook's own entry point; a test of the database alone never counts) and parses what one part writes with the schema the reading part uses, ruling FAIL and naming the test to add when one is missing ([#137](https://github.com/devesh911/revenue-os/pull/137)). The done rules' refusal of a test that reads source code as text (scripts/done-gate/source-reading.ts) also catches, since [#137](https://github.com/devesh911/revenue-os/pull/137), a code file imported with options (`with { type: "text" }`, `type: "file"`), the options written there or held in a name, createReadStream, and a read whose comment claims a fixture; that hole is narrowed, not closed: a read through a renamed reader (`const { file } = Bun`), a shell command such as `cat`, a child process, `fetch` of a file's address, an import whose path is a call (`import(join(…), options)`), a path built from pieces, a read through a name on a line that also names a data file, or a source path named only on a line the change didn't add still passes (stays open). Its ruling counts only from its own delivered report, whose last line is the ruling (`Ruling: PASS — …`): the message of its SubagentHandback call in auto mode, otherwise its last message when it handed nothing back, read by hooks before the Agent and SubagentHandback calls and at its stop (scripts/done-gate/verifier.ts); only from a verifier an Agent call of the session started (a workflow script's verifier never counts) and only when every reply in its own transcript came from claude-opus-5-5, the one model the gate allows, which its instructions name and a verifier call may not change; the ruling covers the code of each checkout the verifier ran a command in (where a `cd` or `git -C` took it; a path it only reads or names does not count), as that code was at its last command there, and a hand-back after that code changed is refused. Rulings are kept in a record only this code writes (`delivered`), so one an older copy of the gate recorded from a typed command never counts; a branch cut before this change runs its own older gate at a verifier's stop, so a ruling on it counts at merge only after it merges main in and is verified again. When a ruling the verifier delivered does not count, Devesh is told why. When it starts, the gate hands it, in at most 9,000 characters, the roadmap item of each checkout the session worked in, as ROADMAP.md on origin/main words it (found by the branch's description, which is never handed over as the item), and Devesh's typed messages from Claude Code's transcript of the session, newest first, those typed while the agent was busy included (a script's prompts marked as script output). Codex reads hooks from the main checkout, not from a worktree. The Codex hooks are proven by running their commands as Codex does, not yet in a live Codex session, and run only once trusted in Codex's /hooks. ## Tests proven

scripts/done-gate/tests-proven.ts, run by `bun run gate` (its "tests proven" check, on the shared local stack one run at a time) whenever a change has product code; CI's `checks` job is set to run it too (`bun run gate proven --base`), not yet seen on GitHub. Both runs happen in scratch clones of the commit the change left main at, with its git history and packages installed (scripts/done-gate/code-copy.ts): the change's copy holds every file the change touches, main's holds all of them but product code, so its tests, helpers and fixtures come along, a new product file that only tests name included (scripts/done-gate/test-only.ts); neither holds what git ignores. A test counts as new or edited when the change adds a line inside it or deletes one from it (scripts/done-gate/test-edits.ts). On main an assertion failing or the test throwing counts; in a test file that can't load there, each test counts on its own, only when the file lacks a product file or export the change adds and that test, run alone with coverage, runs an added line of it more often than loading the file does. A test that passes on main must say why at the end of its first line or alone on the comment line above it (`// behaviour already on main: <why>`); the marks are read from each test file for every test the change touches, marks already on main and the gate's own tests included, shown at every stop and in CI's log, and rules-from-main refuses a pull request whose body doesn't copy each (scripts/done-gate/already-on-main.ts). A test MAY_SKIP lists is noted, not judged, when it skips on either side. Lines the change only moves are left out: the check reads the `moved` mark the snapshot puts on each line git saw move ([#135](https://github.com/devesh911/revenue-os/pull/135), scripts/done-gate/test-edits.ts), so a renamed or reshuffled test file is not judged as new. A stop counts the tests proven, and a stop without Docker leaves this check to CI with the other database checks. About 2 s for a typical change. Missing: a line moved to a test's very end, with a new test right after it, can make git count that test's closing line as added, so it is judged; a block git sees no move in (under 20 letters and digits) is judged as new; only bun's tests run, not the browser checks; both runs use the same local database, which already holds the change's migrations, so a test of a new migration passes on main and must carry the mark; a test changed only through a shared helper or a table outside its own call is not judged; a test of non-product code the change adds (the gate's own, say) passes on main's copy, which holds that code, so in a change with product code it must carry the mark; a test that needs a file git ignores fails in the change's copy and is refused; a new helper whose file name another non-test file happens to quote as an import would counts as product code, and so does an edited (not new) helper under a product folder; two tests with one name in one file both run when either is run alone; a mark the check doesn't take (inside a test, or at the end of code above it) is still shown and asked of the PR body; on a machine without Docker it doesn't run (CI runs it)

## The break check

scripts/done-gate/break-check.ts with broken-lines.ts, run by `bun run gate` (its "break check", after "tests proven", on the shared local stack) and by CI's `checks` job (`bun run gate broken --base`), not yet seen on GitHub. Scope is the one list `GUARDED` in scripts/done-gate/broken-lines.ts: the guard() pipeline and calling hours (packages/harness/src/policies.ts, quiet-hours.ts), the agent loop that runs guard() before each tool (loop.ts), the send doorways (packages/channels/src/) and the two send handlers, the guardrail settings and their API, packages/db/src/ but schema.ts, the sign-in check (services/worker/src/auth.ts) and the API routes' membership checks (services/worker/src/routes/), and metering (packages/harness/src/meter.ts). For each line a change adds there (moved lines, comment-only edits and lines holding no code left out, as the coverage check reads them), a copy of the change gets up to two broken versions of the file: the first condition on the line flipped (=== and !==, == and !=, < and >=, > and <=, "and" and "or", true and false, a leading ! dropped, else a bare if/while condition or a ternary's negated) and the statement the line starts removed (or, on a line holding whole list items, a property or an argument, those items); a version Bun's transpiler can't read, or one that runs the same as the original (a type), is dropped. The test files that import the file, directly or through others, run once with coverage; each break then runs only those that ran its line, stopping at the first that fails; a failing assertion, a test throwing or a run that hangs past 3 minutes counts as caught. A break nothing catches fails the check naming the file, line, the broken line and the test files that ran, unless the line carries `// break-check gap: <why>`, shown at every stop and in CI's log and quoted in the PR body (`Break-check mark:`, refused by rules-from-main without it). Its own time limit is 15 minutes; when it runs out the check fails naming each line not yet broken. Missing: SQL is never broken (TypeScript only), so a company filter inside a query's text is left to the database-policy check and the cross-company tests; the code is read token by token, not parsed, so a rare shape (a regex after `)`, JSX text) may be misread, and a misread break that no longer parses is dropped rather than reported; each break runs whole test files, not only the tests that ran the line; a test file outside apps, services, packages and tests (scripts/) never counts; a flaky database test failing by chance counts as catching a break.
