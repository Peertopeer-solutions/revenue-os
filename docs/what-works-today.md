## Tenant isolation

packages/db/src/client.ts withOrg; RLS on all 36 tables (tests/rls_coverage.sql). A record can't point at another company's: each of the 46 links between company records names the company too (the 43 of migration 019, the 2 of migration 021's sends and the 1 of migration 026's role assignments), and the 7 that may point at a shared template (agents, workflows, eval scenarios with no company) are guarded by the trigger app.same_company_or_template instead (migration 019); every duplicate-protection key names the company, api_keys.key_hash aside; tests/rls_coverage.sql fails a new link or key that could cross companies, and tests/company-links.test.ts tries every link the database lists. Every query the product runs also names its company (org_id = $n; a shared template's read, (org_id = $n or org_id is null); the company row, id = $n), a second fence on top of row-level security: tests run the console's task, contact, conversation, dashboard-count and transcript reads, through the API too, the guard checks, the AI's prompt and update_contact, and the agent-turn, call, WhatsApp, scheduler and enrolment jobs with the database's rules switched off (the local owner login) and see only the company's own rows; the other queries (the trends, agents and guardrail reads, which filtered by company already, the dead-letter and Vapi-processing jobs, contact import, companies and members) are not run that way, and the guard holds their filters (packages/db/test/company-filter.test.ts, services/worker/test/company-filter-api.test.ts, company-filter-jobs.test.ts, packages/harness/test/company-filter.test.ts), and `bun run guards` fails a query that leaves it out (row below). ## Sign in and sign out

apps/console/src/app/session: public /login with a safe return-to, a signed-in gate on every other page, a membership gate with a no-access page, cached data wiped on sign-out. Accounts are invite-only: the local sign-in server refuses a self sign-up, with a password or an emailed code (supabase/config.toml; the test server's own switch waits on Devesh), every worker route but /health, /ready, /release and Vapi's webhook refuses a caller without a valid sign-in token (services/worker/src/auth.ts, PUBLIC_ROUTES; a token must name a user and carry an expiry), and only our operator list creates a company. ## Call results

Webhook receiver works (services/worker/src/vapi); a call id and a provider's event id are kept per company, so another company's event with the same id is neither dropped nor filed on this company's conversation; an event that can't be filed is marked failed with its reason (webhook_events.error) and the company's other events still go through, while a failure of the database itself (a lost connection, a deadlock, a cancelled or timed-out statement) fails the whole job, which runs again, and marks no event failed; a failed event stays failed until someone sets it back to received. Vapi's message times are taken as it sends them, epoch milliseconds (its API reference types them a number; the receiver refused every such message before 2026-10-18), and a time sent as text is read by Postgres as before. A call's conversation is opened by openConversation under its call id, whichever of its events or the job that placed the call comes first; a later open only fills in what is missing (lead, run, agent) and keeps the earliest start time, so a call we place starts when the job placed it, and a call in at its first event, or at its end-of-call report's own startedAt when that report is filed first. Each transcript line is added by addMessage with Vapi's time for it, and the end-of-call report finishes the conversation once (finishConversation) with how the call ended, from endedReason: did-not-answer is no_answer, busy is busy, voicemail is voicemail, an error or failure is failed, anything else completed; its endedAt, else its timestamp, is the end time. An end-of-call report whose AI reading (its analysis.structuredData) says doNotCall: true blocks the call's lead from every later message and call: the conversation's own lead or, on a call no lead is linked to (every call that comes in), the company's leads with the caller's number as their phone or WhatsApp number; any other reading, or a number no lead has, blocks nobody, and a reading never lifts a block or grants consent. The block is recorded first, on its own, so a part of the report that can't be filed (an end time Postgres can't read, or one too large for a date) still leaves the lead blocked; only a report whose call can't be filed at all (a call id too long for its key) records no block. The call's outcome is not saved (Slice 4)

## Conversations

Every conversation and message is written by packages/db/src/conversations.ts, and `bun run guards` fails any other insert, update or delete of either. openConversation: a call is the company's one conversation for its call id, whichever of its events or the job that placed it comes first; a later open fills in only what is missing and keeps the earliest start, so a call we place starts when the job placed it. A lead's message with no call id (WhatsApp now) goes on the lead's newest open thread on that channel, which follows the newest run; two opens at once for one lead take turns, so they make one thread. Anyone else gets a new conversation. addMessage gives each line the next seq under a lock on the conversation, so two writers at once keep every line in order (an AI turn holds no lock while its model thinks, so a WhatsApp send meanwhile becomes the next line and the turn then saves no out-of-date answer), and keeps the event's own time. finishConversation finishes once with a status and, when given, one of the company's dispositions as the outcome, refusing a key the company doesn't have; a later finish only fills what is missing. No production path passes an outcome before Slice 4, and nothing finishes a WhatsApp thread yet

## Deployment

Staging migrations are applied by .github/workflows/staging-migrations.yml only after `checks` has passed on that same commit of main, which it asks GitHub, and only when the commit changed a migration file or the cloud test database lacks one main has (`supabase migration list`); otherwise its apply step shows as skipped. Devesh can re-run it by hand (Actions → staging-migrations → Run workflow, on main). If a migration fails there, every later run stops at it, and the run's summary points Devesh at docs/runbooks/staging-migration-failed.md, the way out no agent can take alone. ## Monitoring and readiness checks

Structured logs; /ready (its own bearer token, READY_TOKEN: refused for everyone when unset, a missing or wrong one refused with 401) answers 200 only when the worker reaches its database and its job queue, each within 2 seconds, else 503 naming only what it could not reach (services/worker/src/ready.ts), and a database connection dropped while idle or while a unit of work holds it no longer ends the worker: idle, the pool hears it (services/worker/src/db.ts); held, withOrg hears it, that work fails and the pool hands out a fresh connection (packages/db/src/client.ts, packages/db/test/with-org-dropped.test.ts); /release, behind the same token, names the commit in RELEASE or "unknown"; every worker image is labelled with the commit it was built from (org.opencontainers.image.revision): docker/Dockerfile refuses a build that names no commit id (compose passes RELEASE through, so a compose build without it fails there), and CI's image build passes github.sha, fails on a wrong label and checks that a build without RELEASE is refused; the image's HEALTHCHECK asks /ready (Slice 1's image proof step, imageNamesItsCommit, sees the container turn healthy), so a container without READY_TOKEN is never healthy; seen on Devesh's Mac with the local stack and Docker: Slice 1's two worker proof steps passed (a worker process with its database cut off and restored, and the image run until Docker reported it healthy and its /release named its commit); no server runs the image yet (the tested-image deploy is Slice 2); no alerts (Slice 6)

## Sequences never stop silently

services/worker/src/call-stops.ts, called by the call job (services/worker/src/handlers/place-call.ts) and the scheduler (services/worker/src/scheduler.ts). A call the calling hours hold back is tried again an hour later, and the call attempt the scheduler counted for it is taken back, as the lead was never rung. Do-not-call, the company's call limit or any other refusal, no active agent and no number each fail the run with the reason saved and one review task on the lead. A run parked on a call wakes an hour after the call was queued: while its job or dead letter is still queued, retrying or running in pg-boss, it waits another hour; otherwise it folds the result the call's own events filed (a voicemail routed as no answer), or hands the lead to a person (no result came, the dialer's answer was never saved, or the call was never placed), and never places the call twice. A run the scheduler can't drive (a missing or broken sequence, a step that keeps failing to apply) gets a review task too. Proven on the real database and pg-boss with pretend providers (services/worker/test/never-stops-silently.test.ts); the dialer is a stub and nothing enrols a lead in the live product, so no real call has gone through it. A run parked on a call before this change has no wake-up time, so it is not picked up

## A role is rows

Migration 026 (supabase/migrations/026_role_versions.sql), packages/shared/src/role.ts (RoleVersionSchema, RoleRulesSchema) and models.ts (the platform's model list: Claude Opus 5.5, Sonnet 5.5 and Haiku 5.5, each as `provider:model-id` with its context size and price), packages/db/src/agents.ts (liveVersion) and assignments.ts (setAssignment). A role version is an `agents` row naming its model, prompt, goal, rules (the next steps it may take and how often, when it asks or hands over to a person, which tools need approval, its outcome names, the appointment kind it books and its holding message), tools, company-facts sections and test set; the seed packs' sales roles name Claude Sonnet 5.5. The database starts every version as a draft, refuses any change but its status once it is tested, and puts it tested, then live, only with one stored run of its whole test set, every row passed, against its exact content; a live version is archived, never edited or taken back. Each turn reads the role's live version when it starts (a new version reaches each lead at its next turn), whole and checked, so a model off the list or rules that don't parse fail the turn before any model is asked; the model it names is the one asked, its goal follows its prompt, its tools read its approval rules (which only tighten) and its booking rule (the appointment kind and the outcome's name), and each usage row names the version. The step map's booking step names its own outcome. Which role works a lead is one row per lead (active, paused, with a person or ended), set by setAssignment, the one writer, from PUT /orgs/:orgId/contacts/:contactId/assignment (operator or admin): a lead is enrolled with a role or in a sequence, never both, which startRun and setAssignment each refuse, locking the lead first so two at once can't both pass. Not yet read by anything: facts sections (company knowledge, Slice 3), the next-step actions and limits (the planner and the contact limits), the ask and hand-over rules and the holding message (the tools and the fallback step); no turn runs from an assignment yet (the wake-up function, Slice 3)
