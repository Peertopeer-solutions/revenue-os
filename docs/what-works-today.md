## Tenant isolation

packages/db/src/client.ts withOrg; RLS on all 34 tables (tests/rls_coverage.sql). A record can't point at another company's: each of the 43 links between company records names the company too, and the 7 that may point at a shared template (agents, workflows, eval scenarios with no company) are guarded by the trigger app.same_company_or_template instead (migration 019); every duplicate-protection key names the company, api_keys.key_hash aside; tests/rls_coverage.sql fails a new link or key that could cross companies, and tests/company-links.test.ts tries every link the database lists. Every query the product runs also names its company (org_id = $n; a shared template's read, (org_id = $n or org_id is null); the company row, id = $n), a second fence on top of row-level security: tests run the console's task, contact, conversation, dashboard-count and transcript reads, through the API too, the guard checks, the AI's prompt and update_contact, and the agent-turn, call, WhatsApp, scheduler and enrolment jobs with the database's rules switched off (the local owner login) and see only the company's own rows; the other queries (the trends, agents and guardrail reads, which filtered by company already, the dead-letter and Vapi-processing jobs, contact import, companies and members) are not run that way, and the guard holds their filters (packages/db/test/company-filter.test.ts, services/worker/test/company-filter-api.test.ts, company-filter-jobs.test.ts, packages/harness/test/company-filter.test.ts), and `bun run guards` fails a query that leaves it out (row below). ## Sign in and sign out

apps/console/src/app/session: public /login with a safe return-to, a signed-in gate on every other page, a membership gate with a no-access page, cached data wiped on sign-out. Accounts are invite-only: the local sign-in server refuses a self sign-up, with a password or an emailed code (supabase/config.toml; the test server's own switch waits on Devesh), every worker route but /health, /ready, /release and Vapi's webhook refuses a caller without a valid sign-in token (services/worker/src/auth.ts, PUBLIC_ROUTES; a token must name a user and carry an expiry), and only our operator list creates a company. Phone code, Google and admin authenticator codes are not built

## Call results

Webhook receiver works (services/worker/src/vapi); a call id and a provider's event id are kept per company, so another company's event with the same id is neither dropped nor filed on this company's conversation; an event that can't be filed is marked failed with its reason (webhook_events.error) and the company's other events still go through, while a failure of the database itself (a lost connection, a deadlock, a cancelled or timed-out statement) fails the whole job, which runs again, and marks no event failed; a failed event stays failed until someone sets it back to received. Vapi's message times are taken as it sends them, epoch milliseconds (its API reference types them a number; the receiver refused every such message before 2026-10-18), and a time sent as text is read by Postgres as before. An end-of-call report whose AI reading (its analysis.structuredData) says doNotCall: true blocks the call's lead from every later message and call: the conversation's own lead or, on a call no lead is linked to (every call that comes in), the company's leads with the caller's number as their phone or WhatsApp number; any other reading, or a number no lead has, blocks nobody, and a reading never lifts a block or grants consent. The block is recorded first, on its own, so a part of the report that can't be filed (an end time Postgres can't read, or one too large for a date) still leaves the lead blocked; only a report whose call can't be filed at all (a call id too long for its key) records no block. The call's outcome is not saved (Slice 4)

## Deployment

Staging migrations are applied by .github/workflows/staging-migrations.yml only after `checks` has passed on that same commit of main, which it asks GitHub, and only when the commit changed a migration file or the cloud test database lacks one main has (`supabase migration list`); otherwise its apply step shows as skipped. Devesh can re-run it by hand (Actions → staging-migrations → Run workflow, on main). If a migration fails there, every later run stops at it, and the run's summary points Devesh at docs/runbooks/staging-migration-failed.md, the way out no agent can take alone. It has run after every push to main since 2026-10-02, each time only once `checks` had passed, and skipped its apply step because the cloud already held every migration; on the one commit whose ci failed it was skipped; a run that applies a migration and a hand re-run have not been seen yet; the worker runs only by hand behind a temporary tunnel, with no tested image, readiness gate or rollback (Slice 2); Cloudflare built and published the console from git on every push, whether or not `checks` passed or the console changed, until 2026-10-13, and has built nothing since: no Cloudflare check appears on a commit of main after the repository moved to the Peertopeer-solutions organisation, which Cloudflare's GitHub app must be installed on (Slice 5); the marketing site is not published yet (its Pages project `krate-www` waits on Devesh); production is off. Caddy is set up for a Cloudflare origin certificate on `API_HOST` with only 443 published (docker/), but the server's address leaked and must change before the api DNS record exists

## Monitoring and readiness checks

Structured logs; /ready (its own bearer token, READY_TOKEN: refused for everyone when unset, a missing or wrong one refused with 401) answers 200 only when the worker reaches its database and its job queue, each within 2 seconds, else 503 naming only what it could not reach (services/worker/src/ready.ts), and a database connection dropped while idle or while a unit of work holds it no longer ends the worker: idle, the pool hears it (services/worker/src/db.ts); held, withOrg hears it, that work fails and the pool hands out a fresh connection (packages/db/src/client.ts, packages/db/test/with-org-dropped.test.ts); /release, behind the same token, names the commit in RELEASE or "unknown"; every worker image is labelled with the commit it was built from (org.opencontainers.image.revision): docker/Dockerfile refuses a build that names no commit id (compose passes RELEASE through, so a compose build without it fails there), and CI's image build passes github.sha, fails on a wrong label and checks that a build without RELEASE is refused; the image's HEALTHCHECK asks /ready (Slice 1's image proof step, imageNamesItsCommit, sees the container turn healthy), so a container without READY_TOKEN is never healthy; seen on Devesh's Mac with the local stack and Docker: Slice 1's two worker proof steps passed (a worker process with its database cut off and restored, and the image run until Docker reported it healthy and its /release named its commit); no server runs the image yet (the tested-image deploy is Slice 2); no alerts (Slice 6)
