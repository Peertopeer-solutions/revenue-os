One lead event, one fresh Pi run, three tools.

A sketch of how a multi-company sales agent built on the Pi coding-agent SDK would work a lead: the database tells it who the company, member and lead are and where the lead is in the sales cycle; the model only proposes the next step; the law, the company's rules and the member's preferences decide; the worker writes what happened as rows. Nothing here runs a model or sends anything.

How does one lead's turn happen?

The flow, lane by lane

Something happens to a lead. The worker, which already exists, fixes the scope from the job itself, builds a bounded context from that one company's rows, and opens a fresh Pi session that lives only for this run. The model calls tools; its proposals pass three layers of checks; the run's results are written back as rows and the session is thrown away.

What does the agent remember, and for whom?

Three memory scopes

A run sits where one member and one lead meet inside one company. It reads all three, but each scope has its own owner: only admins change company rules, only the member changes their preferences, and the model can only add to the lead's own memory.

Company

Holds
Goal, rules (approval setting per action, calling window, weekly call cap, playbook per stage and intent, stages that need a person), product knowledge.
Tables today
guardrail_policies, agents, knowledge_documents, knowledge_chunks
Who writes
Admins, in the console. The model may only suggest; that becomes a review task.
Enters a run
Rules as rows; only knowledge matching the lead's last message, at most three hits.

Member

Holds
Role in this company; preferences such as language, and actions they want to approve first.
Tables today
org_members (role). Preferences have no table yet: future.
Who writes
The member themself. Nobody else, the model least of all.
Enters a run
Role and language as data; approvals as a check that can only tighten.

Lead

Holds
Facts, consent, stage, the conversation, memories (summaries, preferences, objections), intent and next step.
Tables today
contacts, messages, contact_memories, workflow_runs, contact_scores
Who writes
The worker, after the run, from what the model proposed. People may correct it in the console.
Enters a run
Facts and consent always; memories and the newest messages up to their budget.
Which state is the truth?

Rows are the truth; the session is scratch paper

Four kinds of state meet in a run. Only the database's rows are authoritative, which is why every run starts by reading them again instead of trusting a summary from last time.

How does it know where a lead is, and what comes next?

The sales cycle

The cycle runs over the stages contacts already carry (app.lifecycle_stage). The code fixes which stage may follow which (SALES_CYCLE); the company's playbook lists the nurturing moves for each stage and each intent, and a move fits only when both list it. The model never changes a stage itself: it names the stage a step moves the lead to, the checks judge that move with the step, and the worker writes it.

Stage and intent together

Priya is contacted and needs more details: both lists hold a call, so a call fits. Were she an opportunity, the same intent leaves only "wait", and a call would need a person.

A stage moves with a step

propose_next_action takes an optional stage. Confirming an agreed visit by WhatsApp with meeting_scheduled is permitted; jumping from contacted to customer is refused by the cycle.

Who writes it

The worker, after the run, as the lead's stage plus an outcomes row: future work. Moves the company wants to see (here: customer, lost) wait for a person first.

Where does the agent's freedom end?

Every proposal passes three layers

The model never acts; it proposes. A proposal meets the legal floor (code, which no setting can loosen), then the company's policy, then the member's preference, which can only add approvals. Any refusal wins; otherwise any approval wins; otherwise it is permitted, and even then it is only a saved step that the product's existing guard() checks again at the moment of sending.

What happens when a lead needs more details?

The phone-call path, end to end

Devesh's example: a lead asks things a message can't carry well. Intent and stage point the playbook at a call; the lead's memory says when; the checks decide. Everything after "next step saved" is either existing code or a stub, so this prototype stops at the proposal.

How can one company's data never reach another's run?

Isolation, at every door

The run's identity comes from the job, never from the model, and every door is built around it. No tool takes an id, and a call carrying one anyway is refused before the tool runs.

Repository and tools

openScope refuses a lead of another company or a user outside it. The reader it returns takes no ids, and every tool closes over it, so the model cannot name another lead. In the product: withOrg plus org_id in every query.

Retrieval

Knowledge search filters by company first, then ranks; memories by company and lead. Retrieved text enters fenced as data, and no line can close its fence.

Sessions

One fresh in-memory Pi session per run, never resumed for another lead, never written to disk, and nothing loaded from disk: no extensions, skills or AGENTS.md.

Memory writes

The model writes only to this lead. A fact that sounds company-wide becomes a review task for an admin; company rules change only in the console.

How big is the context, and what does compaction do?

A fixed budget per section, rebuilt every run

Each section has its own token budget, so a long conversation can never crowd the rules or the lead's consent out of the prompt. Older messages are dropped first and counted.

Why compaction is not memory

  • It summarises this run's history only; the next run starts fresh from rows.
  • A summary is lossy: a consent change or a promised call time could be paraphrased away. Consent, stage and next steps are rows, re-read every run, and the checks read rows, never summaries.
  • It costs a model call of its own, and can fail when the provider is down.

Who updates memory, and when

  • Lead: the model proposes with remember_about_lead; the worker writes contact_memories after the run, superseding rather than editing.
  • Member: only the member, in the console.
  • Company: only admins. A model's company-wide idea waits as a review task.
Which parts of Pi does this use?

The Pi pieces, and what each is set to

Pi's own agent loop does the turn-taking; this prototype only composes it. Everything Pi would otherwise discover from the machine is supplied explicitly (the pattern of Pi's examples/sdk/12-full-control.ts).

Pi pieceSet toWhy
createAgentSessionCalled only in openLeadSession, which returns the session unpromptedThe host decides whether and when to run the model; nothing here calls it
tools + customToolsAllowlist of the three lead tools, defined with defineTool and TypeBox schemasPi's own read, bash, edit and write tools are not on the list; no sending tool exists
ResourceLoaderHand-written: no extensions, skills, prompt templates, themes or AGENTS.md; fixed instructions plus fenced contextNothing on the machine can change what the agent is told; Pi adds only the working directory, fixed to /lead-run
SessionManagerinMemory()One run's scratch history; the database is the record
SettingsManagerinMemory(): compaction on (keep 8,000, reserve 4,096), cache warming offNo settings files read; no model request the host did not ask for
model, modelRuntimeBrought by the hostThe prototype holds no credentials and picks no model
What is real here?

Built, placeholder, future, and what already exists

Built and tested
  • Tenant-scoped reader that takes no ids
  • Proposal checks: law, company, member
  • Sales cycle: stage order, a playbook per stage and intent, stage approvals
  • Context per scope, budgeted, fenced
  • Memory write rules per scope
  • Pi options: tool allowlist, loader, in-memory session and settings
  • Session factory that never prompts

  • Intent: keyword rules, no score, says so
  • Companies, members, leads: made up
  • Knowledge search: shared words, not embeddings
  • Outbox: held in memory, not written

  • A measured intent method
  • Tools: read history, send WhatsApp, schedule the next touch, hand over (Slice 3)
  • Worker writing the outbox; approval tasks
  • Member preferences table
  • Token and spend limits per lead (Slice 3)

  • withOrg and row-level security
  • guard() and the channel doorways
  • Contact-memory retrieval and its fence
  • Tables: contacts, messages, tasks, guardrail_policies, contact_memories

Open questions, deliberately left for Slice 3

Should Pi's loop replace runTurn in packages/harness/src/loop.ts, or sit beside it until it passes the test conversations?

Should a run's Pi transcript be kept, as rows in messages or as an export, for audit and the data loop?

One session per event (this sketch) or one per lead resumed across events? Per event keeps every run anchored to fresh rows.
